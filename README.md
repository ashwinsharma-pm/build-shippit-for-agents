# Build Shippit for Agents

A single-page strategy document arguing that Shippit's fulfilment workflows must be rebuilt **agent-native** — exposed as typed, callable, policy-bounded capability an agent can find, call, pay for, and trust — before someone builds an agent-native logistics layer around us.

> Build for humans, as well as agents.

## What's here

- **`index.html`** — the complete, self-contained document. Carbon Bold + Space Grotesk fonts are inlined as data-URIs, so it renders anywhere with zero external dependencies or build step. Sticky table-of-contents with scrollspy, reading-progress bar, and a responsive single-column layout under 880px.

## The argument, in ten sections

1. **The shift** — the operator of the Shippit workflow is changing from a human to an agent.
2. **The thesis** — rebuild every shipping workflow agent-native.
3. **Old vs agent workflow** — the same jobs, run a different way.
4. **The agent's journey** — Find → Evaluate → Trust → Transact → Use → Recommend.
5. **What agents need** — six building blocks: Identity, Tools, Inbox, Memory, Wallet, Receipts.
6. **Examples today** — AgentMail, Stripe, Slack, executable support: the blocks already exist in other categories.
7. **An agent-readable Shippit** — `/agents` entry point, capability manifest, schemas, policies, MCP tools, SDK + OAuth.
8. **What this changes** — six shifts from concrete to agentic workflows.
9. **Early ideas** — capacity exchange, autonomous returns, Rules Engine copilot, lane reputation graph, promise agent.
10. **The prediction** — the next phase of Shippit is built for agents as well as humans.

## Design

Visualize Value (VV) aesthetic — inverted palette (white ground, black marks), two typefaces with strict roles (Carbon Bold for data/labels, Space Grotesk for reading), flat surfaces, hairline rules, no shadows or gradients.
